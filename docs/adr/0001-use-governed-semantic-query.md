# 使用受治理的 SemanticQuery，而不是让模型生成 Raw SQL

自然语言问题先被转换成只引用已发布语义成员的结构化 `SemanticQuery`，再由确定性内核规划和编译 SQL。该选择牺牲了任意 SQL 的表达能力，并要求我们维护语义 DSL 和编译器，但能够在执行前统一校验指标口径、Join 安全、权限和查询预算，也使不同数据库方言共享同一分析意图；第一版无法表达的问题会被明确拒绝，而不会绕过语义层。

## Consequences

- `SemanticQuery` 是跨服务的核心版本化契约，不能包含物理表列、Join 条件、公式字符串或任意 SQL 表达式。
- SQL 文本只是编译产物，不是 Agent 的输出，也不是分析正确性的主要评估对象。
- 扩展分析能力必须先演进语义模型和编译器，并通过兼容性与回归测试。
